# AGENTS.md

Instructions for coding agents working on **Assay** itself. If you are using Assay in
*your* project, the section below is what `assay agents init` writes into your repo.

## Setup

```bash
pip install -e packages/assay-core -e packages/assay-cli -e packages/assay-mcp
```

Windows: `start-assay.bat fresh` does this and starts the workbench.

## Checks — run these before finishing

```bash
pytest packages/assay-core/tests        # ~5s, run constantly
pytest tests/e2e                        # real binary, real port, real stdio
assay lint && assay spec validate .     # the shipped artifacts still conform
python tests/mutation/run_mutations.py --check    # ~1s
```

`assay test` exits 4 on eval failure. `pytest tests/e2e` needs the CLI installed.

## House rules, in order of how much trouble breaking them causes

1. **Never report a number that overstates what was measured.** An unverified run says
   *not checked*, never *passed*. A rate computed from zero usable samples is withheld,
   not shown as 0%. A governance control states its gap beside its evidence. This is the
   product's entire argument; code that violates it is a bug even when tests pass.
2. **`verified` is tri-state.** `None` means nothing was checked. Do not coerce it.
3. **A test that cannot fail is worse than no test.** If unsure, break the code on
   purpose and confirm it goes red. Two tests in this repo asserted orderings that held
   regardless of the values they claimed to test; mutation testing caught both.
4. **Unknown fields in a PromptFile must round-trip untouched.** That is what lets a file
   written today survive a tool written in five years.
5. **The spec key is `promptfile:`, not the product name.** See ADR-0009.

the workbench reads. TypeScript types are erased at runtime and check nothing about what
the server actually sends.

## Prompts and agents in this repository

This repository uses [Assay](https://github.com/BaijayantaRoy/Assay) to keep prompts and
agents as files. Each one is a **PromptFile** — YAML frontmatter plus a Markdown body,
carrying its template, model binding, guardrails and **its own test cases**.

They live in `prompts/`. There are 5 of them, including 1 agent harness and 1 verified loop.

**Before writing a new prompt, check whether one already exists here.** Reusing a tested
artifact is nearly always better than writing an untested one inline.

## What is available

| id | kind | inputs | tested | what it does |
|:--|:--|:--|:--:|:--|
| `agents/code-reviewer` | agent | `diff`, `focus`, `language` | yes | A review agent that reports only defects it can point at, with an explicit no-findings… |
| `agents/researcher` | harness | `goal` | yes | Searches a codebase before answering, and is tested on that order. |
| `loops/verified-pipeline` | loop | — | yes | A two-step loop where each handoff is verified, not just the final result. |
| `shared/house-style` | system | — | yes | Shared writing constraints, included by other prompts rather than copy-pasted. |
| `support/refund-triage` | prompt | `customer_tier`, `message` | yes | Classifies inbound support messages into a routing queue with a confidence score. |

Bodies are deliberately not reproduced here — they would spend your context budget on
material you did not ask for. Fetch one with `assay show <id>`.

## Commands

All of these work offline against a deterministic `echo` provider, so they need no API key
and cost nothing to run.

```bash
assay ls                             # list every artifact with its id
assay show <id>                      # full source of one artifact
assay render <id> -v key=value       # fill the template, no model call
assay run <id> -v key=value          # execute against the bound model
assay test                           # run every embedded eval — exit 4 on failure
assay test <id>                      # just this one
assay lint                           # validate against the PromptFile spec
```

**`assay test` is the check to run after editing anything under the prompts directory.**
It exits non-zero on failure and needs no network.

## Agent harnesses

- `agents/researcher` — Searches a codebase before answering, and is tested on that order.

A harness declares its own tools, budget, memory and controls, and every run produces a
**trajectory**: the record of what the agent actually did. Assertions check the path, not
just the final answer — an agent can reach the right result through a tool call it should
never have made.

```bash
assay run <harness-id> -v goal='...'   # run it, get the trajectory
assay redteam <harness-id>             # measure its injection defences
```

## Editing rules

- **Do not paste prompt text into code.** Reference the artifact by id and render it, so
  there is one copy and it stays tested.
- **A new artifact needs at least one eval case.** An artifact with no evals passes every
  run by default, which is not the same as working.
- **Run `assay test` before finishing.** If it fails, fix the artifact rather than
  loosening the assertion.
- **Do not edit generated blocks** between the `assay:begin` and `assay:end` markers in
  this file; run `assay agents init` instead.
